# M02-W0203 - Role registration, role changes, cooldown and NEXT-wave queuing

Deterministic role engine in `backend/internal/simulation/role.go`. It accepts
already-canonicalized, authorized role commands and applies them to the
authoritative state. Text parsing, Unicode normalization, Vietnamese diacritics,
punctuation rejection and provider identity mapping remain M03-W0301; raw comments
never reach this layer.

## Command contract

```go
type RoleCommand struct {
    InputSeq      int64
    ActorKey      domain.ActorKey
    Role          domain.Role
    TargetWave    int64
    ScheduledTick int
}
```

Rules enforced before any mutation (a whole batch is rejected atomically):

- `InputSeq` positive and unique within the batch; commands are processed in
  ascending `InputSeq` order.
- `ActorKey` is a valid scoped 64-hex identity; `Role` is one of the three domain
  roles, never a raw string.
- `ScheduledTick` must be inside the current wave, strictly after the committed
  tick, and never retroactive.
- Current-wave commands must target the current wave; RESULTS commands
  (tick 2800..2999) must target `current+1`.
- The first registration in WAITING must be effective at tick 0.

## Public API

| Item | Value |
|---|---|
| Entry | `ApplyRoleCommands(state, []RoleCommand) (state, []RoleEvent, []RoleDecision, error)` |
| Internal outcome | `RoleDecision` (registered, role_changed, duplicate_same_role, cooldown_rejected, next_wave_queued, deferred_while_paused); may carry the private actor key for durable acknowledgement |
| Public events | `role_registered`, `role_changed`, `next_wave_queued`, `role_cooldown_rejected`; never contain an actor key, provider id, alias or comment |
| Aggregates | `ActiveCounts(state, boundaryTick)`, `IsContributionBoundary(tick)` |
| Errors | `ErrInvalidCommand`, `ErrDuplicateInputSeq`, `ErrRetroactiveInput`, `ErrSourceDisconnected`, `ErrStorageUnavailable` |

## Behavior

- **WAITING start:** the first valid registration reuses the W0202 `start_wave`
  transition: tick 0, PREP, one member with `joined_tick=0`, no last change, first
  switch available, no XP and no resource change. Operator START alone still
  cannot create a participant.
- **Registration:** one membership per actor per wave, joined at the effective
  scheduled tick, canonical order by actor key.
- **First switch:** accepted immediately after joining; preserves `joined_tick`,
  sets `first_switch_used=true` and the accepted logical tick in
  `last_change_tick`.
- **Cooldown:** later changes require `scheduled_tick - last_change_tick >= 600`.
  A rejected change preserves role and bookkeeping, consumes no cooldown and
  emits only a rejection signal.
- **Same-role duplicate:** deterministic no-op; no event, no cooldown reset, no
  membership growth. 1,000 repeated commands still produce exactly one
  membership.
- **RESULTS (2800..2999):** role choices queue the NEXT wave without touching
  current membership, enemy state, votes or XP. The pending queue is deduplicated
  and canonically sorted; a queued role can be updated once immediately, and a
  second queued change is cooldown-bounded by the same 600-tick rule while the
  finishing wave runs. Promotion at rollover gives the new member
  `joined_tick=0` with a fresh first switch, because roles and cooldown state
  expire at rollover per the binding rules. This interpretation is deliberate and
  documented here: no cross-wave cooldown penalty is invented.
- **Pause states:** operator pause defers commands (`deferred_while_paused`, no
  mutation); a disconnected source rejects new commands; storage-unavailable
  rejects input that could not be durably acknowledged. Durable queues and
  connectivity checks belong to M03/M04 and are not claimed here.

## Boundary contribution

`ActiveCounts` counts members whose `joined_tick` is at or before the boundary:

- effective at 199/200 contributes at the tick-200 boundary;
- effective at 200 contributes at tick 200;
- effective at 201 does not contribute at tick 200;
- a role change effective at 400 applies at the tick-400 boundary.

No builder production, damage, guard block, boss interaction, vote or XP is
implemented or claimed.
