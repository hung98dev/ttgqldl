# M02-W0202 - Deterministic tick state machine, lifecycle and rollover control

Pure logical progression layer under `backend/internal/simulation`. It owns the
clock, lifecycle, pause reasons, phase boundaries, rollover control and
deterministic transition events. It implements no combat, vote, economy, XP,
persistence or network work.

## API

| Item | Value |
|---|---|
| Entry point | `Next(state domain.SessionState, input Input) (domain.SessionState, []Event, error)` |
| Kinds | `start_wave`, `advance_tick`, `rollover`, `pause`, `resume`, `stop` |
| Inputs | explicit pause reason, explicit accepted registration, optional `FromTick` stale-request guard |
| Errors | `ErrInvalidState`, `ErrInvalidInput`, `ErrNotRunning`, `ErrTickFrozen`, `ErrStopped`, `ErrNotAtRollover`, `ErrControlBoundary`, `ErrOutOfOrder`, `ErrNoRegistration`, `ErrUnsettledWave`, `ErrOverflow` |
| Events | `wave_started`, `phase_changed`, `paused`, `resumed`, `stopped`, `rolled_over`, `schedule_boundary`, `settlement_required` |
| Boundaries | `vote_close`, `population_lock`, `role_resolution`, `boss_spawn`, `combat`, `final_combat`, `rollover` |
| Stages at 2800 | `consume_inputs`, `final_contribution`, `final_combat`, `settlement`, `enter_results` |

Every call validates its input state, works on a deep copy, validates the result
and never mutates or partially applies state on error.

## Tick rules implemented

- WAITING is tick -1 and cannot advance.
- A wave starts only from an explicit accepted registration at tick 0; operator
  START alone, a timer or a fabricated participant can never start it.
- Exactly one tick per `advance_tick`; stale `FromTick` requests are rejected.
- Phase is derived from the tick on every transition; no separate phase clock.
- Tick 3000 is reached by one advance but only a rollover consumes it, and no
  gameplay resolution runs there (no phase change, no settlement).
- Entering tick 2800 emits the ordered stages below and leaves the result
  pending: W0202 never settles a wave or declares victory.
- Pause reasons freeze the tick; clearing one of several does not resume; clearing
  all resumes with no catch-up ticks.
- Rollover: exactly one wave increment, wave state reset, village/XP/streaks
  preserved, pending registrations promoted with `joined_tick=0`, running at tick
  0 when the queue is non-empty, otherwise WAITING at -1. A paused session cannot
  roll over until resumed, and an unsettled wave cannot roll over at all.

## Boundary scheduling order

| Tick | Boundaries in canonical order |
|---|---|
| 1200 | `vote_close`, `role_resolution` |
| 1600 | `population_lock`, `role_resolution` |
| 1800..2780 (multiples of 200) | `role_resolution`, `combat` |
| 2600 (boss wave) | `role_resolution`, `boss_spawn`, `combat` |
| 2800 | `role_resolution` (final contribution), `final_combat` (never duplicated), settlement requirement, then the RESULTS phase notification |
| 3000 | `rollover` only |

The boss spawns after role contribution and before the attack phase, matching the
binding order in `02_GAME_RULES.md`. Non-boss waves never emit `boss_spawn`.

## Settlement ordering contract

At tick 2800 the events are, in this exact order, with an explicit `stage`:

1. `schedule_boundary` `role_resolution` `final_contribution`;
2. `schedule_boundary` `final_combat` `final_combat`;
3. `settlement_required` `settlement`;
4. `phase_changed` to RESULTS with `enter_results`.

The state's wave result stays `pending`, so a phase notification can never be
mistaken for a completed settlement. W0205 and W0207 must run those stages in
order; W0202 only publishes the schedule. Rollover requires a non-pending result
and fails closed with `ErrUnsettledWave` otherwise, and it rejects wave-number
overflow with `ErrOverflow`.

## Remediation (2026-11-04)

Source review found three scheduling/settlement defects and one evidence defect.
They are fixed and covered by regression tests.

| # | Defect | Fix |
|---|---|---|
| 1 | At tick 2600 on a boss wave the boundary order was `role_resolution`, `combat`, `boss_spawn`, so combat appeared to precede the spawn | order is now `role_resolution`, `boss_spawn`, `combat`, matching the binding rules; ordinary combat boundaries stop at 2780 so tick 2800 is only `final_combat` and is never counted twice |
| 2 | Entering 2800 published RESULTS before the final-combat and settlement signals | events at 2800 are now an ordered contract with explicit stages: `final_contribution`, `final_combat`, `settlement_required`, then `phase_changed` with `enter_results`; the wave result stays pending so a phase notification cannot be mistaken for settlement |
| 3 | Rollover could advance past an unsettled wave (`Result == pending`) | rollover fails closed with `ErrUnsettledWave`; the state, pending queue, XP and resources are untouched. Wave-number increments also reject int64 overflow with `ErrOverflow`. Tests use an explicitly identified synthetic settled fixture because real settlement is W0207 |
| 4 | The evidence file contained embedded control characters that corrupted API, event and file names | the file is rewritten as clean UTF-8, and `planvalidate` now fails any Markdown containing control characters other than tab/CR/LF (`text-integrity`, with a seeded-defect test) |

Scope is unchanged: W0202 schedules work and never settles a wave, spawns an
enemy, awards XP or fabricates a victory. The 2800 stage list is the structure
W0205/W0207 must fill; QA-SIM-10 and QA-SIM-11 gameplay execution are still owned
by later packages.
