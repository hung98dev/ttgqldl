# M04-W0401 — PostgreSQL writer epoch fencing

Status: **PASS** for W0401's single-writer lease/fencing boundary. M04 remains
IN_PROGRESS; W0402–W0407 are NOT_STARTED. This evidence does not claim reducer

QA-DB-07 completion.

## 1. Implemented contract

New package `backend/internal/writer`:

- `Manager.Acquire(ctx, villageID)` — atomically acquire or take over a village lease.
- `Manager.Renew(ctx, lease)` — heartbeat; never changes the epoch.
- `Manager.Release(ctx, lease)` — conditional release by owner+epoch; never decrements.
- `Manager.WithFence(ctx, lease, sessionID, fn)` — authoritative fenced transaction.
- `Manager.Close(ctx)` — bounded conditional release.
- `Manager.Epoch()` / `Manager.Status()` — fail-closed readiness integration boundary.
- `FencedTx` exposes only `Exec`, `Query`, `QueryRow`; no `Commit`/`Rollback`.

State transitions:

```text
no row/epoch0 ──acquire──▶ epoch1 owner A
epoch1 owner A ──renew───▶ epoch1 owner A (new expiry)
epoch1 owner A ──expiry──▶ epoch1 owner A (invalid)
expired/owner null ──acquire B──▶ epoch N+1 owner B
epoch N owner A ──release──▶ epoch N owner null, session epoch0
```

A same-owner valid acquire is idempotent and keeps the epoch. Reacquisition by the same
instance after expiry allocates epoch+1. `math.MaxInt64` and negative stored epochs fail
closed with `ErrEpochExhausted`/`ErrInvalidEpoch`; no wraparound.

## 2. PostgreSQL transaction and locking strategy

- Acquisition first ensures the lease row (`INSERT ... SELECT ... ON CONFLICT DO NOTHING`),
  then `SELECT ... FROM ttg.writer_leases WHERE village_id=$1 FOR UPDATE`.
- The committed owner/epoch/expiry are read only under that row lock. Expiry is evaluated
  with `clock_timestamp()` **after** the lock, never transaction-start `now()`, so a
  transaction that waited through expiry cannot use a stale start timestamp.
- Acquisition/takeover updates the lease and the active session's `writer_epoch` plus
  `last_heartbeat_at` in the same transaction, then commits. Success is returned only
  after commit.
- Lock order is `writer_leases` → active `sessions` row. W0305 ingestion locks only the
  session row and does not acquire the lease, so there is no reverse lease/session cycle.
- `WithFence` locks the lease row, checks owner/epoch/expiry, locks the caller's session
  row, verifies session village/epoch/stopped state, runs the callback, and only then
  commits. The lease row lock is held through the protected write; takeover waits.
- Release locks the lease, verifies owner/epoch and unexpired state, clears owner/expiry,
  sets the active session `writer_epoch=0`, and commits. The lease epoch is retained.
- `runTx` retries only SQLSTATE 40001/40P01, at most three attempts; commit errors are
  never retried blindly and return `ErrCommitUnknown`.
- No schema migration was required; existing `writer_leases` and `sessions` fields are
  sufficient. No sqlc generated code changed.

## 3. Stale-writer proof

The unsafe interleaving is prevented by the lease row lock:

1. A fenced transaction locks `writer_leases` and verifies epoch N/owner A/expiry.
2. It holds that row lock while performing the protected write.
3. A takeover transaction must lock the same row; it cannot update epoch N+1 until A
   commits or rolls back.
4. If A waits for the lock until after expiry and B commits N+1 first, A's subsequent
   `clock_timestamp()`/owner/epoch check fails and its callback never runs.
5. If A held the lock before B, A's write commits before B's generation; B then owns N+1.
   No commit by A with epoch N can occur after B's N+1 commit.

`TestDelayedStaleTransactionCannotCommitAfterTakeover` proves the mandatory barrier with
real PostgreSQL: B holds the lease lock with epoch2 uncommitted; A's fenced transaction
waits; B commits; A fails and its callback flag remains false.
`TestDelayedLockWaiterUsesDatabaseClockAfterLock` holds the lease row, starts B before
expiry, waits through expiry, releases the row, and verifies B takes over with epoch+1
because it evaluates `clock_timestamp()` after the lock.

## 4. Real PostgreSQL test results

24 writer tests against PostgreSQL 18.6 (all run, none skipped; `TTG_REQUIRE_DATABASE=1`):

- first acquisition: epoch1, owner/expiry stored, session epoch1;
- same-owner acquire keeps epoch1;
- 8 synchronized contenders: exactly 1 owner, 7 `ErrLeaseHeld`, one epoch1 row;
- renewal: epoch unchanged, DB expiry advanced; wrong owner/epoch `ErrLeaseLost`;
- expiry: renew and fenced write fail `ErrLeaseExpired`; callback not called; release fails;
- takeover: B epoch2; A renew/release/fence all fail; B fenced write succeeds;
- delayed stale transaction: A callback never runs after B commits epoch2;
- delayed lock waiter: B takes over after DB-clock expiry with epoch+1;
- rollback injection: no lease row and session epoch0 survive;
- unknown commit: `ErrCommitUnknown`, committed epoch1 visible, retry reconciles to same
  epoch1 (no new generation, no dual owner);
- closed pool: `ErrStorageUnavailable`, no verified local state;
- release: wrong owner cannot release; release keeps epoch for the next generation;
- Close: conditional release, local epoch0, second Close safe;
- village isolation: A contention does not fence B; manager cannot silently own two
  villages (`ErrManagerBusy`);
- session lifecycle: waiting/running/paused/source_disconnected/storage_unavailable update
  epoch and fence; stopped session has no active epoch and fence returns
  `ErrSessionInactive`; recreated active session is resynchronized;
- fenced callback rollback: protected write absent; session mismatch `ErrSessionMismatch`;
  stale session epoch `ErrStaleEpoch`;
- epoch overflow/negative: `ErrEpochExhausted`/`ErrInvalidEpoch`, no wraparound;
- concurrent 12 renew + 12 fenced writes: all succeed, epoch unchanged;
- local expiry readiness: `Epoch()`/`Status.Verified` become false without claiming DB
  authority (fail-closed local guard).

## 6. Readiness, security and privacy

- `Manager.Epoch()` returns 0 when no lease is verified or the local view is past its
  recorded expiry; `Status.Verified` is false in the same case. This is a fail-closed
  local guard only; it cannot grant ownership. The M01 server remains dormant: it does
  not instantiate a writer, so `/readyz` reports 0 unless a real manager is injected.
- No HTTP lease endpoint, admin bypass, raw SQL exposure to clients, credentials in logs,
  provider identities in diagnostics or public pool expansion was added.
- Validation rejects empty/overlong/control instance IDs and malformed village/session
  UUIDs. Errors are typed and privacy-safe; no IDs or SQL text are echoed.
- PostgreSQL time is the sole expiry authority; local wall time only removes a local
  readiness claim, never authorizes acquisition or writes.
- M03 ingestion remains a separate transaction boundary; no W0305 semantics changed.
  M02 gameplay constants, tick ordering, RNG, canonical hashes and `ttg-rules-v1` are
  unchanged.

## 7. Known limitations

- W0402 reducer/outbox/atomic tick commit, `applied_at_tick`, wave membership, ballots,
  resources, domain events, stream outbox and checkpoints are not implemented.
- No background heartbeat worker; callers must invoke `Renew` explicitly. W0402 owns the
  runtime loop and shutdown integration.
- The fenced API is a trusted internal surface; callers can still issue arbitrary SQL
  through `FencedTx` (without Commit/Rollback). W0402 must keep callbacks transaction-only
  and not mutate lease authority.
- QA-DB-05 and QA-DB-07 remain partial: full reducer/outbox atomicity, 1k/s batch order
  and mixed pause/outage behavior are later work.
- No schema migration was necessary; existing table constraints are unchanged.
