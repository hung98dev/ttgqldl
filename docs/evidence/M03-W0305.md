# M03-W0305 — Durable batched input ingestion

Status: **PASS** for W0305's durable append boundary. PostgreSQL 18.6 is authoritative:
accepted candidates are appended as immutable `input_events` with consecutive per-session
`input_seq` values, stable-ID receipts carry fingerprint+association, and acknowledgment
happens only after commit. W0305 does **not** mutate reducer state, mark events applied,
implement writer fencing/checkpoints/recovery, or claim QA-CMD-02/QA-DB-06/QA-DB-07
complete. M04 remains responsible for those.

## 2. Migration and SQLC changes

Forward-only `00005_input_receipt_integrity.sql`:

```sql
ALTER TABLE ttg.input_receipts
  ADD COLUMN payload_fingerprint CHAR(64),
  ADD COLUMN input_seq BIGINT;
CHECK (payload_fingerprint IS NULL OR payload_fingerprint ~ '^[0-9a-f]{64}$')
CHECK (input_seq IS NULL OR input_seq > 0)
FOREIGN KEY (session_id, input_seq) REFERENCES ttg.input_events(session_id,input_seq)
  ON DELETE RESTRICT
CREATE INDEX input_receipts_unassociated ON ... WHERE input_seq IS NULL
```

Existing rows are preserved with explicit NULL associations (historical receipts cannot
prove which event they acknowledged). The unique constraint is unchanged. Down migration
refuses to drop associations while any receipt exists; the destructive migration lifecycle
test proves up/down/re-up on PostgreSQL 18.6. `db/schema.sql`, `schema.fingerprint.json`
and SQLC v1.31.1 output (`inputs.sql.go`, `models.go`) were regenerated; `sqlc diff` and
`TestSchemaFingerprintMatches` are clean.

## 3. Durable receipt and conflict semantics

New receipts store the compact 32-byte W0304 fingerprint as 64 lowercase hex plus the
allocated `input_seq`. Durable lookup distinguishes:

- first insertion → append;
- same event id + same fingerprint → duplicate returning the prior sequence/event;
- same event id + different fingerprint → conflict, no sequence and no event;
- receipt acknowledged but response lost → retry is a duplicate;
- transaction rollback → no receipt/event/sequence;
- committed event but in-memory reservation expired → receipt remains authoritative.

Historical NULL-fingerprint receipts are treated as duplicates without a conflict claim.
Provider event ids remain scoped by `(session, provider)` and are never viewer identities.

## 4. Atomic append transaction

One transaction per session batch:

1. `SELECT ... FROM ttg.sessions WHERE id=$1 FOR UPDATE`.
2. Validate mode/provider (`mock`/`replay`; `authorized_live` rejected), lifecycle
   (waiting/running/paused/source_disconnected allowed; stopped/storage_unavailable
   rejected) and rules version.
3. Derive target wave/tick from committed state only.
4. Check receipts and classify duplicate/conflict.
5. Allocate consecutive `input_seq` from `sessions.input_sequence`; BIGINT overflow is
   rejected before any write.
6. Insert immutable `input_events` (`applied_at_tick` stays NULL), then receipts.
7. Update `sessions.input_sequence` once.
8. Commit, then acknowledge.

No wave members, ballots, resources, XP, combat, checkpoints, domain events or outbox rows
are touched. A missing stable event id never fabricates a receipt but still receives a
durable sequence. Retries are limited to 3 by default and only for SQLSTATE 40001/40P01.

## 5. Sequencing and scheduling

Sequences are per session, consecutive, unique under concurrent batches, independent
across sessions, never reset by reconnect and never derived from Go counters, provider
time, cursors, randomness or process start. Concurrent 10×10 batches produced exactly
1..100 with no duplicates.

Scheduling from committed state: WAITING/tick<0 → current wave tick0; tick 799→800,
1198→1199, 1199→1200, 1598→1599, 1599→1600, 2599→2600, 2799→2800; RESULTS at tick
2800/2999 → next wave tick0. `accepted_tick` equals the committed session tick. W0305 does
not advance ticks or mutate lifecycle. Two concurrent WAITING registrations receive tick0
and distinct sequences; the reducer's existing one-start rule remains authoritative (W0305
does not claim start ownership).

## 6. Batching and backpressure

`Batcher`: bounded FIFO queue (default 20,000), one worker, max batch 256, 50 ms deadline.
A full batch flushes immediately; an incomplete batch flushes on the injected timer. Queue
saturation returns explicit `ErrQueueFull` (source callback fails, cursor does not advance;
no silent drop) and increments `RejectedQueue`. `Close` stops admission, drains and flushes,
and waits for the worker. Stats expose queue depth/high-water, batches, transactions,
inputs, duplicates, conflicts, commit-unknown and errors. No acknowledgment precedes
commit.

Measured with real PostgreSQL: 256 submissions → 1 batch/1 transaction/256 inputs; 257 →
2 batches (256+1); 255 with injected timer → 1 batch; real 50 ms timer flushed 10 inputs in
the 40 ms..2 s bound; queue capacity 2 rejected the next submission explicitly.

## 7. Failure, retry and ambiguous commit

- Simulated crash after inserts but before commit → rollback leaves no receipt, event or
  consumed sequence; retry succeeds with sequence 1.
- Simulated lost acknowledgment after commit → `ErrCommitUnknown`; receipt lookup proves
  the row and a retry returns the prior duplicate; the batcher reconciles to a committed
  outcome and does not release the reservation.
- Synthetic 40001/40P01 errors retried within budget (success on attempt 2); exhaustion
  returns `ErrRetryExhausted` with no rows.
- Closed/unreachable PostgreSQL returns `ErrStorageUnavailable`; no acknowledgment.
- Sequence overflow (`MaxInt64-1` plus two inputs) returns `ErrSequenceOverflow` with no
  writes.
- Disk-full/write failure was not safely injectable on this host; the transaction rollback
  path is the same as the tested pre-commit failure, and no disk-capacity benchmark is
  claimed.

## 9. Privacy

`input_events` stores only `actor_key`, typed canonical JSON (`{"kind":"role","role":...}`
or `{"kind":"vote","ballot":...}`), scheduling and rules version. Raw provider viewer ids,
aliases and comment text are never fields of `DurableCandidate` or `input_events`; a test
checks the payload and table columns. Stable provider event ids remain in the private
receipt table only. No secrets appear in SQL diagnostics; `authorized_live` is rejected.
