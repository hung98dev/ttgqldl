# M02-W0208 - Golden fixtures, canonical hash and deterministic replay

Implemented scope: production-reducer golden boss vectors P=10 and P=30, canonical
RFC 8785 projection and SHA-256 state hash, and a 110-position checkpoint/restart
replay harness. **Status is IN_PROGRESS** because the QA-BAL-05 fighter-share
curve and the broader golden matrix are not yet executed.

## Golden vectors (production reducer, synthetic wave-5 fixture)

Fixture: fresh village, 10/30 roles joined at tick 0, wave 5, no vote. This is an
explicitly documented mathematical fixture, not a recorded playthrough.

## Canonical state and hash

`backend/internal/canonical`:
- `Project` builds the versioned documented field set (schema/rules versions,
  session/village ids, wave/tick/lifecycle/defeated, village resources and
  progression, anchor/difficulty/base_hp, lane pools, boss, vote with ballots,
  members with `session_xp`/`xp_awarded`/nullable `last_change_tick`, queued next
  wave, privacy epoch);
- `MarshalJCS` emits RFC 8785 canonical JSON: sorted keys, no whitespace, no
  floats (unsupported types rejected), explicit nulls, int64 decimal strings;
- `Hash` returns the hex SHA-256 of those bytes.

Tests: JCS known vectors (key ordering, arrays, null/bool, large int64, escaping),
determinism, unsorted-member rejection, foreign rules/schema rejection,
nullable-field explicitness, and sensitivity to wood/wall/role/`xp_awarded`/
session XP/privacy epoch/change tick.

## Replay

`replay_017_test.go` runs uninterrupted traces and reconstructs 110 checkpoint
positions by replaying the prefix from the initial fixture, then resuming with
deep-copied state and queue. Every subsequent canonical hash, the final state and
the event stream are compared. Corruption tests change resources or the rules
version and must fail hash verification.

### 3. Replay Scenarios A/B/C/D — one common driver

driver. It records, per step: `scenario_id, wave_no, committed_tick, phase,

the role/ballot queues and `reflect.DeepEqual` on the complete emitted event slice

### 2. Restored queue contract (derived from role.go, vote.go, clock.go)

- The role queue holds **only current-wave work**. NEXT-wave registrations are
  promoted to the authoritative `SessionState.Pending` collection at acceptance
  (`queueNextWave`), so one can never legitimately remain in
  `RoleQueue.Entries`. The legal RESULTS lifecycle is proven with a production
  fixture: `AcceptRoleCommands` during RESULTS leaves the queue empty and writes the
  pending member; rollover promotion is unchanged.
- A running session accepts a command at or before the committed tick and makes it
  effective strictly after that tick. Anything scheduled at or before the committed
  tick would already have been applied and is rejected as stale.
- A WAITING session may hold the wave-start registration: accepted at the `-1`
  sentinel, effective at tick 0, targeting the current wave.
- A pending ballot is pinned to the next committed tick: acceptance requires
  `scheduled_tick == committed_tick + 1`, and a ballot whose tick is reached is
  applied before a checkpoint can observe it. Ballots require an even wave.
- Ballot actors must be current-wave participants effective at the ballot's
  scheduled tick, exactly the `AcceptVoteCommands` rule.
- Both queues persist in deterministic `(scheduled_tick, input_seq)` ascending
  order, the order `sortQueue` / `sortBallotQueue` produce.
- Input sequences are positive and unique across both kinds; queued ballots may not
  reuse an already-applied input sequence.
- Paused state never invalidates a legitimate future command, because the logical
  clock is frozen.

Regression tests: `TestCheckpointQueueStaleCommands`,
`TestCheckpointQueueBallotEligibility`, `TestCheckpointQueueOwnership`,
`TestCheckpointQueueOrdering`, `TestCheckpointQueueAlreadyAppliedBallot`,
`TestCheckpointQueueAcceptsLegitimateStates`.
