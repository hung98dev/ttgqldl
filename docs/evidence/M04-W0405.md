# M04-W0405 — Encrypted physical backup, WAL archive and PITR restore

Status: **PASS** for the scoped W0405 physical PITR rehearsal. M04 remains IN_PROGRESS;
W0406/W0407 are NOT_STARTED. Production RPO/RTO, nightly scheduling, seven real retained
restore points and privacy-safe cutover are not claimed.

## 1. Architecture

- Pinned PostgreSQL `18.6@sha256:3a4264520e121176619f54ff867d12774bc81e95e7b84db58d63bccdb6144b81`.
- Disposable primary container with separate Docker volumes for PGDATA, WAL archive and
  base backups; the test removes the primary PGDATA volume while backup/WAL volumes stay.
- `archive_mode=on`, `wal_level=replica`, `archive_timeout=60`, and an atomic
  `archive_command` using a temp file, `sync`, conflict rejection and rename.
- `pg_basebackup -Fp -X stream` into the independent backup volume, tarred, AES-256-GCM
  encrypted on the host, SHA-256 manifest, and restored into a new isolated PostgreSQL
  container with `restore_command`, `recovery.signal` and `recovery_target_*`.
- Encryption key is generated in the test process and never written to the repository or
  logs. Manifest key reference is a reference only.

## 2. Real rehearsal result

`TestRealEncryptedPhysicalBackupAndPITR` (Docker, real PostgreSQL 18.6):

- Migrations applied to version 8.
- Synthetic village/session + W0402 reducer revision R=1 committed; canonical hash and
  tick recorded.
- Real physical base backup after R; backup plaintext **50,298,880 bytes**, encrypted
  **50,298,908 bytes**; manifest SHA-256 verified.
- Revision R+1 committed after the base backup; WAL forced and archived (archive volume
  ~32 MB).
- Primary container and PGDATA volume deleted; backup and WAL volumes preserved.
- Restore to a time marker between R and R+1: revision **1**, exact canonical hash,
  W0403 `VerifyReplay` PASS.
- Restore to the LSN after R+1: revision **2**, exact canonical hash, W0403 replay PASS.
- Restore durations **~3.1 s each**, total test **~40.2 s** including base backup,
  encryption, archive wait, primary deletion and two isolated restores.
- Missing-WAL negative: the segment containing the target LSN was removed from an
  isolated archive copy; the restore container failed and never became ready.

## 3. Integrity and negative tests

- Wrong AES-256-GCM key: `ErrDecrypt`; tampered ciphertext: authentication failure.
- Manifest validates backup ID, PostgreSQL version, system identifier, WAL start/end,
  timeline, size, ciphertext/plaintext SHA-256, encryption format, verification and
  restore eligibility; incomplete/unverified manifests are rejected.
- `PlanRetention` keeps at least seven verified/WAL-complete restore points and refuses
  to delete a point whose required WAL is needed by a retained point; six points fail
  closed. Dry-run dependency planning only; no destructive retention against live data.
- `PrivacyGate` is fail-closed: client serving is denied unless an independent external
  deletion ledger is available, verified, covers the restore time and erasures are
  replayed. PostgreSQL tombstones alone are not accepted.
- The isolated restore is not exposed as a public/client-facing service; W0406 remains
  NOT_STARTED and is the required privacy gate before any cutover.

## 4. RPO/RTO scope

This is a **small local synthetic fixture**, not production-scale evidence:

- RTO observed ~40 s for the full rehearsal on local Docker; this is not a production
  RTO<=30 min claim.
- WAL `archive_timeout=60` and continuous archiving are configured, but RPO<=5 min is not
  proven by a configuration value or this tiny fixture.
- No nightly scheduler, seven real retained backups, archive-destination outage,
  storage-full, wrong-major-version or PITR timeline-history rehearsal was executed.
- Production must use separately protected storage, external key management, monitoring
  and a representative restore rehearsal; local volumes are not site-level resilience.
