# M03-W0306 — Ingress metrics, queue observability and drop accounting

Status: **PASS** for W0306's observability boundary. It adds bounded, race-safe counters,
queue/batch/durable-stage observations, commit-latency buckets, alert state and explicit
loss accounting. It does **not** claim the full QA-CMD-02 or QA-LOAD-01 requirements:
reducer application, 10k load, M07 dashboard integration and durable alert routing remain
open.

## 1. Confirmed W0305 defect and repair

Audit of `Batcher.flush` found that every append error, including an unresolved
`ErrCommitUnknown`, released the W0304 reservation. Reproduced against pre-fix commit
`95e6b5c` in an isolated worktree with a fake appender returning `ErrCommitUnknown` and a
fingerprint-verified lookup returning not-found:

```text
REPRO unknown=ingest: commit outcome is unknown; durable reconciliation required
      pending=0 stable=0
FAIL: pre-fix released reservation on unknown commit
```

Root cause: the error path called `releaseReservation` for all errors before checking
whether the commit outcome was ambiguous. Fix: an unresolved unknown outcome responds with
the error but leaves the reservation pending; only definitive failures release. Regression
`TestMetricsUnknownCommitDoesNotReleaseReservation` asserts `Pending=1, StableEntries=1`
after the unknown result, `CommitUnknownOutstanding=1`, and successful finalization on a
later retry. `TestMetricsPostgresDurableOutcomes` verifies the reconciled path commits
exactly once and clears outstanding.

## 2. Implementation and wiring

New `backend/internal/ingest/metrics.go`:

- Fixed-size `Metrics` with atomic counters and a 15-bucket latency histogram; no maps,
  labels, per-event objects or raw identifiers.
- `Metrics.Handler()` read-only JSON endpoint; GET only, `Cache-Control: no-store`.
- `Deduper.Config.Metrics` records exactly one final W0304 classification per admission.
- `BatcherConfig.Metrics`/`Now` records enqueue, queue depth/high-water, in-flight batch,
  batch/transaction counts, durable committed/duplicate/conflict, failures, unknown commit
  and reconciliation, caller cancellation and receive-to-commit latency.
- Source/parser stages expose explicit `ObserveReceived`, `ObserveValidated`,
  `ObserveInvalidGrammar`, `ObserveOversized`, `ObserveInvalidIdentity`,
  `ObserveUnauthorizedSource`; the test pipeline calls them at the real boundaries.
- `RecordDroppedGameEvent(DropReason)` is the only path that increments confirmed loss.

Not wired: the M01 server skeleton has no ingestion pipeline, so `TTG_METRICS_ADDR` is
validated but no endpoint is mounted and no zeros are exported as live telemetry.
`Metrics.Handler` is the integration boundary for M04/M07; when mounted it must bind the
configured loopback/private address and remain read-only.

## 3. Counter vocabulary and stage semantics

Stage counters: `input_received`, `input_validated`, `accepted_candidates`, `enqueued`,
`durable_committed`, `durable_duplicates`, `durable_conflicts`.

Rejection/classification counters: `invalid_grammar`, `oversized`, `duplicate_provider_id`,
`conflicting_provider_id`, `repeat_noop`, `rate_limited`, `invalid_identity`,
`ignored_non_command`, `capacity_exceeded`, `queue_overflow`, `unauthorized_source`,
`storage_unavailable`, `commit_unknown`, `retry_exhausted`, `batch_failures`,
`caller_cancelled`, `reconciled`, `lost_game_events`.

Reserved reducer/moderation vocabulary: `cooldown` and `blocked_user` exist as explicit
counters but W0306 never increments them; only M04/M07 may. `gameplay_applied` is JSON
`null` (not 0) because no reducer metric exists; this distinguishes “unavailable” from
“zero applied”.

One event can appear in several stage counters (received → validated → accepted →
enqueued → committed), but only one final classification counter. Duplicate durable
delivery increments `durable_duplicates`, never `durable_committed` or `inputs`.

## 4. Queue/batch and latency observations

`queue_depth` is channel occupancy only; `in_flight` is the batch held by the worker. Both
are exposed so they are not confused. Also exposed: capacity, utilization, high-water,
enqueued, queue_overflow, batches, transactions, inputs, max batch, durable outcomes,
failures, commit unknown/reconciled and fixed-bucket p50/p95/p99 (upper bucket bound) with
sample count. Queue capacity remains 20,000; max batch 256; flush 50 ms. Latency is
measured only from enqueue to confirmed durable result; no fabricated sample is created
when no commit occurs.

## 5. Loss accounting invariants

- Invalid/non-actionable events: classification counters only; never loss.
- Duplicates/no-ops: duplicate/repeat counters; never loss.
- Queue full: `queue_overflow` + `ErrQueueFull`; source cursor does not advance; **not**
  counted as permanent loss.
- Caller cancellation after enqueue: `caller_cancelled`; durable outcome may be unknown;
  never loss.
- Ambiguous commit: `commit_unknown` + outstanding count; not durable success and not
  loss until resolved. Verified reconciliation increments `reconciled` and clears the
  outstanding count.
- Confirmed loss: only `RecordDroppedGameEvent` increments `lost_game_events` and raises
  permanent `DROPPED_GAME_EVENT` degradation. No automatic code path silently discards a
  valid action.

## 6. Alert state

Bounded `AlertState` with `unknown/ok/warning/degraded`:

- queue utilization strictly >75% for 30 consecutive seconds → warning
  `QUEUE_UTILIZATION_HIGH`; exactly 75% does not trigger; dropping to ≤75% clears.
- internal p95 >1s for 5 minutes with at least 20 samples → warning
  `INTERNAL_LATENCY_HIGH`; fewer samples never alert; low p95 clears.
- confirmed lost game event → degraded `DROPPED_GAME_EVENT` (permanent).
- storage unavailable → degraded `STORAGE_UNAVAILABLE`; recovery clears storage only.
- unresolved commit unknown → warning `COMMIT_UNKNOWN`; reconciliation clears.
- no observation → `unknown`, never healthy.

`SnapshotAt(now)` evaluates sustained queue/latency at an injected instant so a scrape can
raise a sustained alert without new submissions; the handler uses the same path.

## 8. Privacy and security

Metrics contain fixed field names and counts only. Tests assert the JSON does not contain
`provider_viewer`, `actor_key`, `comment`, `secret` or `session_id`, and a 1,000 unique-id
cardinality test keeps the payload below 4 KiB with no event ids. No raw provider ids,
aliases, comments, tokens or arbitrary source-controlled labels are used. Metrics never
mutate simulation state, ordering, RNG, canonical hashes or replay behavior.
`authorized_live` remains gated.

## 9. Known limitations

- M04 reducer application/`applied_at_tick`/cooldown/blocked-user metrics are not
  implemented; `gameplay_applied` is null, cooldown/blocked counters remain reserved.
- M07 operator dashboard, alert routing and paging are not implemented; `Metrics.Handler`
  is not mounted.
- QA-CMD-02 and QA-LOAD-01 remain partial: no 10k population, no sustained 1k/s/5k burst
  acceptance, no reducer behavior.
- The 20k queue and 256/50ms batching are tested structurally; no production throughput
  claim.
