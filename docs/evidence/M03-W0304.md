# M03-W0304 — Provider-event deduplication, spam protection and idempotency boundaries

Status: **PASS** for the W0304 in-memory ingress boundary. This package classifies
stable provider-event duplicates, conflicting payload reuse, missing-event-id repeats and
per-actor rate limits; it reserves/finalizes/releases candidates so a failed downstream
operation does not permanently consume an event. It is **not** durable exactly-once
ingestion and does not claim QA-CMD-02 complete: durable receipts, authoritative input
sequence, XP/role persistence and reducer integration remain W0305/M04.

## 1. Stable-ID identity contract

Stable dedupe scope is exactly `(logical session, provider source, provider event id)`.
The cache key is a domain-separated, length-prefixed SHA-256 (`ttg-ingest-stable-v1`);
raw provider event ids are never retained. The same id in another session or provider is
independent; reconnect redelivery is a duplicate; a provider event id is never used as a
viewer id and a viewer id is never used as an event id. Durable uniqueness remains the
database `UNIQUE(session_id, provider_source, provider_event_id)` boundary owned by
W0305.

## 2. Conflict detection

Each stable receipt stores a compact 32-byte fingerprint over the resolved ActorKey,
event kind and canonical typed action (role/ballot family + value). Display alias,
comment spelling/Unicode representation, timestamps and event metadata do not affect the
fingerprint. Classifications:

- same fingerprint → `duplicate_provider_id`;
- different fingerprint → `conflicting_provider_id`, no candidate, first fingerprint is
  never overwritten;
- different kind under the same id (e.g. gift then comment) → conflict;
- different session/provider → independent.

Non-command events with stable ids are recorded only for conflict detection and never
return a reservation. If the bounded cache is full, non-command events are ignored without
recording (gameplay capacity is not blocked); this best-effort limitation is documented.

## 3. Best-effort missing-event-id path

When no stable event id exists and a valid scoped ActorKey is available, a bounded
sliding window per `(session, actor key, canonical action)` suppresses repeats inside the
configured window. The parser's typed canonical action is used, so `XAY`, `XÂY`, `xây` and
`BUILD` are the same Builder action while Guard/Fighter/ballots stay distinct. The window
keeps up to `WindowSamples` accepted timestamps per scope, so suppression follows the last
accepted sample rather than a fixed time bucket; the boundary is strict (`now <
sample+window` suppresses, exactly `window` allows). Server-observed injected time is
used; provider `upstream_at` is ignored. The path is explicitly best effort and never
claims exactly-once gameplay. Missing identity fails closed (`ErrInvalidIdentity`).

## 4. Rate limiting

Per scoped ActorKey token bucket: capacity **10**, refill **0.5 tokens/second** (5 per
10 s). Duplicate/conflict/repeat classifications do not charge. A new accepted candidate
charges one token; `Release` refunds one token capped at capacity; `Finalize` keeps the
charge. Refill clamps negative elapsed time to zero, so clock rollback cannot mint tokens.
Buckets are bounded by `MaxActors`, evicted only after `BucketIdleTTL`, and one expiry heap
item per bucket is re-queued lazily on purge, so the heap cannot grow per event. No negative
balance; exact 2 s refill boundary is tested.

## 5. Reservation lifecycle

`Admit` returns a reservation only for `accept_candidate`. Pending reservations expire
after `PendingTTL`; no reservation is indefinite. `Finalize` commits the in-memory
receipt (stable path) or keeps the accepted sample (best-effort path). `Release` removes
the receipt/sample and refunds the token. Both are idempotent for the same terminal action
and return `ErrReservationClosed` for conflicting terminal actions. Finalizing an expired
reservation refunds and returns `ErrReservationExpired`. The source cursor contract is
unchanged: a downstream failure returns an error before cursor advancement, so redelivery
can retry.

## 6. Bounds, expiry and capacity

- `MaxEntries` bounds stable receipts + window entries; `MaxActors` bounds buckets.
- `StableTTL` (default 10 min) suppresses finalized stable duplicates; `Window` (10 s),
  `PendingTTL` (30 s), `BucketIdleTTL` (10 min) are explicit.
- Expiry uses a deterministic `(time, sequence)` heap with generation checks; only expired
  entries are removed. At exactly the TTL the entry is expired (purge uses `!now.Before`).
- Reaching `MaxEntries`/`MaxActors` with unexpired state returns
  `capacity_exceeded` + `ErrCacheFull`; unexpired receipts are never silently evicted.
  This is deliberate degradation requiring W0305 durable storage.
- No goroutines, timers or background cleaners; cleanup is synchronous on admission.
- Stats expose counts only (`StableEntries`, `WindowEntries`, `Buckets`, `Pending`).

## 7. Concurrency

A single deduper mutex serializes classification, reservation insertion, rate refill and
expiry, so simultaneous submissions of one event id cannot both be first-seen. Tests:
100 goroutines on one id → exactly one accepted; two conflicting payloads → one accepted
and one conflict; 100 unique actors all accepted; parallel capacity never over-admits;
concurrent finalize is idempotent; per-actor rate isolation under parallel load. The race
detector runs in Linux CI.

## 9. Privacy and logging

Cache keys and fingerprints are SHA-256 digests; no raw comments, aliases, provider viewer
ids, event ids or secrets are retained. Errors expose field categories only; Stats exposes
counts only. Raw provider ids are used transiently to derive ActorKeys in the pipeline and
are not stored by ingest.

## 10. HMAC rotation boundary

Stable-id deduplication is independent of ActorKey key version. Best-effort keys use the
resolved scoped ActorKey; without a durable alias mapping, the same person under two key
versions can appear as two scopes and must not be treated as continuous. W0305/M04 will
resolve `actor_identity_aliases` before dedupe/rate scoping. Ephemeral mock/replay
identities remain synthetic and are never treated as authorized LIVE identities.

## 11. Source snapshot disk-bound review

`ReplayConfig.MaxFixtureBytes` (default `DefaultMaxFixtureBytes` = 64 MiB) bounds both the
fixture and its verified snapshot. `NewReplay` rejects oversized files before delivery;
`snapshot(ctx)` checks total copied bytes, cancellation between reads, and temporary-file
create/write/seek failures (`ErrSnapshotIO`). Snapshot I/O and cancellation map to
`DISCONNECTED` (retryable), digest/record/size contradictions map to `FAILED`; no partial
snapshot is ever scanned. Cleanup runs on every failure and on success. Tests cover exact
limit accepted, one byte over rejected, growth after construction rejected, create failure
then successful reconnect, cancellation with empty temp directory, write failure and
successful cleanup. The 50,000-record streaming regression remains.
