# M01-W0103 — Complete PostgreSQL schema, migrations, indexes and sqlc

## Deliverable
The whole schema of `docs/plan/04_DATABASE.md` as executable, forward-tested
goose migrations, plus the sqlc generation pipeline that M03/M04 will consume.

## Schema facts verified against the migrated database
```
tables in schema ttg: 19 (+ goose_db_version = 20 rows in information_schema)
CHECK constraints:    29
FOREIGN KEYs:         14        (all ON DELETE RESTRICT)
PRIMARY KEYs:         19
UNIQUE constraints:    3        (villages.broadcaster_key, players(village_id,actor_key), input_receipts event)
partial/unique index:  sessions_one_active_per_village  WHERE lifecycle <> 'stopped'
partial index:         input_events_pending             WHERE applied_at_tick IS NULL
tables in schema public: 0
```
Note: `goose_db_version` is created inside `ttg` because the owner role runs with
`search_path = ttg`; no object exists in `public`.

## Migration round-trip (actual)
```
$ go run ./cmd/migrate -direction up
OK 00001_core.sql (18.0ms) / 00002_inputs.sql (13.0ms) / 00003_operator_privacy.sql (19.0ms)
goose: successfully migrated database to version: 3

$ go run ./cmd/migrate -direction down -to 0
OK 00003 / 00002 / 00001 → current version: 0   (only goose_db_version remains)

$ go run ./cmd/migrate -direction up
goose: successfully migrated database to version: 3

$ go run ./cmd/migrate -direction down        # one step
current version: 2
$ go run ./cmd/migrate -direction up
current version: 3
```

## sqlc
```
$ cd backend && sqlc generate      # sqlc v1.31.1
$ ls internal/db
db.go  models.go  sessions.sql.go  villages.sql.go
$ go build ./...   # exit 0
$ go vet ./...     # exit 0
```
sqlc reads `db/schema.sql`, never the goose files (which contain down migrations
and markers). Regeneration sequence: `migrate-up` → `schema-dump` → `sqlc generate`.

## Least privilege re-confirmed for the new objects
```
ttg_owner: CREATE ON DATABASE ttgqldl = true   (owner creates schema objects)
ttg_app:   CREATE ON DATABASE ttgqldl = false  → create table ttg.x → "permission denied for schema ttg"
ttg_app:   SELECT/INSERT/UPDATE/DELETE on owner-created tables = allowed via default privileges
```
`schema-dump` connects with `pg_dump` over the container's local socket as
`ttg_owner`; no password is embedded in a script.

## Honest limits
- Greenfield only: there is no data migration, backfill or rollback-of-live-data
  scenario, because no production data exists.
- Retention/partition jobs (input_receipts TTL, audit expiry, outbox pruning) are
  specified in 04_DATABASE.md but not implemented; they belong to M04-W0407.
- `TestSchemaSnapshotMatchesDatabase` compares table sets, not columns; a
  column-only change requires running `tooling/schema-dump` manually (documented
  in `backend/db/queries/README.md`).
- CI applies migrations as the `postgres` superuser of the service container, so
  the `ttg_owner`/`ttg_app` grant model is verified locally (this record, and
  M01-W0102), not in CI.
- No index has been exercised at production data volume; performance evidence is
  M08.
