# M01-W0102 — PostgreSQL 18.6 development infrastructure

## Deliverable
A reproducible, loopback-only PostgreSQL 18.6 development environment with a
pinned image digest, a persistent named volume, health checks and
least-privileged application credentials. No production schema is created
(W0103 owns it).

## Files
- `compose.dev.yaml` — single service, `name: ttgqldl`, image
  `postgres:18.6@sha256:3a426452…b81`, `127.0.0.1:${POSTGRES_PORT}:5432`,
  volume `ttgqldl_pgdata:/var/lib/postgresql`, initdb mount read-only,
  `pg_isready` health check (5s interval, 3s timeout, 20 retries, 15s start
  period), `stop_grace_period: 60s`, `shm_size: 256mb`,
  `security_opt: no-new-privileges`, `mem_limit: 2g`, `cpus: 2.0`.
- `docker/postgres/initdb/001_roles.sh` — creates `ttg_owner` (owns schema `ttg`,
  used by migrations) and `ttg_app` (row-level DML only). Neither is a
  superuser, has CREATEDB/CREATEROLE, or may create objects. `PUBLIC` loses
  CONNECT on the database and CREATE on `public`; both roles get
  `search_path = ttg`.
- `.env.example` — the register values, including the three database passwords
  and the DSN; `.env` is generated from it by `dev-up` and is gitignored.

## Postgres 18 image detail that matters
The 18.x official image sets `PGDATA=/var/lib/postgresql/18/docker` and declares
`VOLUME /var/lib/postgresql`. The compose volume therefore mounts
`/var/lib/postgresql`, not the pre-18 `/var/lib/postgresql/data` path.

Least privilege, verified functionally:
```
current_user=ttg_app  current_schema()=ttg
has_schema_privilege(ttg_app,ttg,USAGE)=true   CREATE=false
has_database_privilege(ttg_app,ttgqldl,CONNECT)=true

ttg_owner: create table ttg.privcheck + insert            → CREATE TABLE / INSERT 0 1
ttg_app:   select/insert/update/delete on that table       → succeeded (default privileges)
ttg_app:   create table ttg.nope                            → ERROR: permission denied for schema ttg
ttg_app:   create role nope                                 → ERROR: permission denied to create role
ttg_owner: drop table ttg.privcheck                         → DROP TABLE   (test artefact removed)
```
Role attributes: `ttg_app|rolsuper=f|createdb=f|createrole=f|canlogin=t`,
`ttg_owner` identical (non-superuser).

## Persistence across restart
```
before down:  select system_identifier from pg_control_system() → 7703936920650424363
./dev-down.ps1   → "development dependencies stopped; the data volume was preserved"
./dev-up.ps1     → container healthy again
after up:     system_identifier → 7703936920650424363   (identical cluster, data preserved)
```
`dev-down` runs `docker compose down` **without** `--volumes`; only
`dev-down --wipe-data` deletes it, and that path asks for an interactive
confirmation and refuses in non-interactive shells.

## Honest limits
- The bootstrap superuser (`ttg_bootstrap`) exists because the image requires
  one; the backend never uses it. It is a development-only credential.
- CI uses a plain `postgres` service container, so the **role bootstrap is not
  exercised in CI**; it is verified here on a real container. A CI step that
  mounts the initdb directory is a W0106 follow-up.
- No schema, index, migration, sqlc query or retention job exists yet — W0103.
- Backups/PITR (QA-DB-01 second half, QA-OPS-03) are not implemented; that is
  M04/M09.
- The compose file is development-only; no production Compose/manifests exist.
