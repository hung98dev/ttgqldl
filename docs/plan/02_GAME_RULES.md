# GAME RULES — BINDING

**Rules identifier: `ttg-rules-v1`.** Every number, formula, ordering and bound below belongs to that identifier. Changing any of them requires an explicit rules identifier bump and, in the SAME commit, updates to 03_SIMULATION.md, 09_QA_ACCEPTANCE.md, 10_IMPLEMENTATION_MATRIX.md and regenerated `tooling/refeval` golden vectors. Silent drift is a FAIL.

## Session/village and progression
One broadcaster owns one village (broadcaster key stable, privacy-protected). Session has one active wave at a time. A village keeps level 1..50 (persisted as `villages.level`; the rule value `village_level` below is the same field), wall tier 1..20, XP cosmetics, resources and persistent total_wins; starts level=1, wall tier=1, wall_hp=1000, townhall_hp=500, wood=400, stone=250, food=300, construction_work=0; resources capped at 1,000,000 each. Initial session state: wave_no=1, wave_tick=-1, lifecycle=waiting, consecutive_wins=0, consecutive_losses=0, total_wins=0. All backend arithmetic signed int64 checked for overflow, never floats.
One wave is 300s at 10Hz (local ticks 0..2999). Start only on first eligible role message after operator START; status WAITING at wave_tick=-1 before that. PHASE is derived from the local tick only: PREP [0,160s)=[0,1600); ASSAULT [160,260s)=[1600,2600); FINALE [260,280s)=[2600,2800); RESULTS [280,300s)=[2800,3000). Boss on wave_no divisible by 5. Engine only advances simulation time while RUNNING; PAUSED, PROVIDER_DISCONNECTED, STORAGE_UNAVAILABLE freeze time. Tick 3000 is ONE control transition, never a gameplay tick: if NEXT-wave roles are queued, promote them atomically and start the next wave at tick0; otherwise WAITING at wave_tick=-1 until a new eligible join. Queued viewers MUST NOT be required to comment again.

## Exact player action model
Text exact role commands XAY/THU/DANH and BUILD/DEFEND/ATTACK; lower-case, trim, Unicode NFKC, fold Vietnamese diacritics incl. đ->d, collapse ASCII/Unicode spaces; only one canonical token accepted; punctuation and substrings are invalid. One role selection registers player for CURRENT wave, except RESULTS where it queues NEXT wave; ONE role contribution at each 20s resolution boundary until RESULTS, even if user sends no more messages. Thus viewers never need to repeatedly comment. `wave_members.joined_tick` is the acceptance tick at which the registration becomes effective (the ingest `scheduled_tick`); a NEXT-wave registration queued during RESULTS is persisted with wave_no=current+1 and joined_tick=0, and is promoted unchanged at tick3000, so it is inside the next wave's population-anchor window. Last VALID role accepted before a boundary takes effect on the next boundary; the first role change after joining is permitted immediately, while subsequent changes require >=600 simulation ticks since the last accepted role change; additional changes are ignored/acknowledged as cooldown, NEVER modify previous role. Repeated identical messages are no-op and do not consume the switch. A player joining RESULTS is assigned to NEXT wave and receives immediate visible 'NEXT WAVE' receipt, without counting as present now; when next wave starts, registration transfers atomically and persists for that wave. A participant joining a paused wave receives queued role only if source is connected, applied on resume without advancing simulation clock. Player roles expire at wave rollover; previous wave XP/identity persist.
A player earns +10 XP once per wave with at least one eligible contributing interval; no XP per chat, repeated comment, vote or gift. XP cap per player per SESSION = 300 and level is cosmetics only. A newly joining viewer contributes equally in the same role as veterans. Display actual accepted count and source health, not fake viewers. IDs are scoped HMAC identities from authorized stable provider ID, otherwise session-only ephemeral with honest limitations.

## Roles and economy
At each positive multiple of 200 ticks up to and INCLUDING tick2800 (which resolves before RESULTS begins), while not DEFEATED, count active registered participants B=builders, G=guards, F=fighters, where ACTIVE at boundary tick t means `joined_tick <= t`. A participant whose joined_tick equals the boundary contributes at that boundary but is not in the anchor unless joined_tick<=1599. Population anchor P = max(1, count of unique registrations with joined_tick<=1599 at tick1600), capped at 10,000 for difficulty coefficients, while all valid viewers beyond 10k still counted in contributions with sqrt saturation cap=10,000 per role. New viewers after tick1600 increase effort but cannot increase that wave's enemy HP, encouraging newcomers. At the SAME boundary, after aggregation and before builder economy, each active member with `xp_awarded=false` receives exactly one +10 session XP (cap 300) and is marked awarded; this award precedes any combat or defeat effect of that boundary.
Builder generation each interval, in this exact order: wood += 2*isqrt(B)+floor(B/50); stone += isqrt(B)+floor(B/500), both clamped to 1,000,000. Repair capacity = 8*isqrt(B). Then repair min(repair_capacity, wall_max-wall_hp, 5*wood) and deduct wood cost ceil(actual_repair/5) using integer arithmetic. Unused capacity (capacity - actual_repair) becomes construction work. Construction work accumulates only if B>0 and is clamped at the current threshold 200*wall_tier until an upgrade consumes it. Upgrade automatically if construction_work >= 200*wall_tier AND stone >= 100*wall_tier AND wall_tier<20: subtract both costs, wall_tier += 1, new wall_max=1000+200*(tier-1), add 200 to wall_hp capped to the new max; at most ONE tier upgrade per boundary; unconsumed construction_work is kept. At tier20 construction work is ignored. Repair always executes before that boundary's combat damage, so repaired HP can absorb the same boundary's retaliation.
Guard block = 8*isqrt(G) each COMBAT boundary, cannot be banked. Fighter attack = 18*isqrt(F), cannot be banked. If 1<=P<=10, non-viewer militia attack bonus max(0,40-4*(P-1)) per COMBAT boundary; if P>10 militia attack=0. Show any militia as system assistance, never count it as a viewer. No NPC appears in statistics as a user or earns XP. All isqrt integer floor.

## Enemies / waves / boss
At tick 1600 snapshot P, difficulty d=min(10,1+consecutive_wins); initial ordinary HP base_hp = max(1, floor((40+8*d+38*isqrt(P))*(100-15*min(consecutive_losses,3))/100)), difficulty reduction is transparent 'recovery modifier' shown on HUD. Enemy pools: west=floor(base_hp*34/100), center=floor(base_hp*32/100), east=base_hp-west-center. Each lane subpools runner=25%, grunt=55%, brute=remainder (integer floors); each subpool has only HP counter and visual archetype, not 10,000 enemy entities. Normal units spawn at tick 1600; deterministic visual counts are for presentation, not hit points.
Boss wave (wave_no divisible by 5): at tick 2600, spawn boss pool with HP ceil(base_hp/5). Before tick2600 the boss does not exist in authoritative state: `boss_hp`=0 and only the derivable maximum ceil(base_hp/5) is known. Non-boss wave: no new enemy, but FINALE warning/visual climax. Boss is in center lane and is attacked after all ordinary subpools in that lane. One initial fixed enemyHP pool for each wave; no hidden rubber-banding after tick1600.
At COMBAT boundaries t=180,200,220,240,260,280s (tick 1800..2800), in this exact order: (1) role/economy contribution and repair; (2) boss spawn if tick 2600 and boss wave; (3) apply fighter+militia attack, vote B modifier 115/100 if active, integer floor; (4) calculate enemy retaliation from surviving ordinary HP and boss; (5) apply guard block with vote A 115/100 or vote C 90/100, floors; (6) subtract damage from wall, overflow into townhall, stopping at zero; (7) emit canonical state and visual cues.
Attack distribution for step (3) is fully deterministic and MUST be implemented exactly as follows, because it changes outcomes. (a) Split the total attack A: lane shares are floor(A/3) for each lane; the remaining A%3 points go one each to the lanes visited in cyclic order starting at start_lane = combat_index mod 3, where combat_index is 0 at tick1800 and increases by 1 for each later combat boundary (1800,2000,2200,2400,2600,2800). (b) Within a lane, damage is consumed in priority runner, grunt, brute, and — only in the center lane and only when the boss pool exists — boss last. (c) Damage left over in a lane after its own pools are empty is redistributed in round 2 over ALL living pools (ordinary subpools and the living boss pool) visiting lanes in the same cyclic order and, within each lane, the same priority; each visit consumes min(pool_hp, remaining) so no redistribution is wasted while a living pool exists. The boss is therefore legitimately killable by redistributed damage. (d) Attack damage is never banked to a later boundary.
Ordinary enemy retaliation before guard block: raw = ceil((10+3*d+9*isqrt(P))*ordinary_remaining/base_hp) when ordinary_remaining>0 else 0; boss surviving after spawn adds ceil((10+3*d+9*isqrt(P))/5). Apply guard block once to TOTAL and max(0,raw-guard_block). If current wall is zero, subsequent damage goes to townhall. If townhall becomes 0, mark DEFEATED immediately and skip all subsequent economic/combat resolutions, damage and XP for this wave; still settle exactly once at tick2800. If all pools empty before results, show CLEAR only if no boss spawn remains scheduled; on boss wave before tick2600 show BOSS INCOMING rather than CLEAR. Attack/retaliation do not happen during PREP or RESULTS.
At tick 2800, AFTER that boundary's combat resolves and BEFORE RESULTS begins, settle exactly once; a repeated settlement call MUST be a no-op. Victory iff townhall_hp>0 and all enemy pools are zero (the boss pool counts when the wave is a boss wave), else loss.
Victory, in this order: wood=min(1,000,000,wood+100); stone=min(1,000,000,stone+60); food=min(1,000,000,food+50); consecutive_wins=min(10,consecutive_wins+1); consecutive_losses=0; total_wins=total_wins+1; village_level=min(50,1+floor(total_wins/3)).
Loss, in this order: consecutive_wins=0; consecutive_losses=min(3,consecutive_losses+1); compute wood_penalty=floor(wood/5), stone_penalty=floor(stone/5), food_penalty=floor(food/5) from the PRE-penalty values; if the chosen option is C halve every penalty with floor(penalty/2); subtract each penalty (never below zero) and clamp each resource to [0,1,000,000].
Recovery floors apply if and only if the wave ended in defeat (townhall_hp reached 0), and are applied AFTER the penalties: wall_hp=min(wall_max,max(250,wall_hp)); townhall_hp=min(500,max(250,townhall_hp)); wood=min(1,000,000,max(100,wood)). A loss without defeat receives no 250 HP floor and no 100-wood floor.
At rollover (tick3000), wave_no=wave_no+1, previous-wave roles/vote/enemies/defeat flags reset, village progress preserved, pending NEXT-wave registrations promoted and the next wave started at tick0 if present, otherwise WAITING at wave_tick=-1.
Vote on EVEN waves only, available for ballot ticks in [800,1199] (that is [t=80,t=120)); one latest ballot per player wins, exact options A/B/C. Only current-wave participants with joined_tick<=1199 can vote. Effects: A costs 50 wood deducted at close and grants +15% guard block for the wave; B costs 50 food deducted at close and grants +15% attack; C is free, costs -10% guard block but halves loss penalties. COSTS ARE CHARGED ONLY FOR THE CHOSEN OPTION.
Selection algorithm at tick1200, executed once, deterministic, no RNG: (1) tally ballots per option; (2) if there are zero ballots, chosen = A when wood>=50 at the close tick else C; (3) otherwise consider options in order of (vote count descending, then A>B>C), and pick the FIRST option that is affordable at the close tick (A needs wood>=50, B needs food>=50, C is always affordable); if no option is affordable, chosen=C. The chosen option is displayed and its effect applies at every later combat boundary of that wave. No vote, and no further comments, are required to keep playing.

## Bounds and anti-spam
Role counts B/G/F can exceed population anchor, but effective counts for formula each capped at 10,000. Never repeat role contribution based on number of comments. Each ID is one player per wave, independent of comment burst. Send feedback only for accepted role/new choices and meaningful events; no invitation to flood or game stats based on comments count. Store alias opt-out and safety filtering. No paid combat advantage.

## Explicit fixtures / initial acceptance cases
One player XAY: NPC militia makes solo P=1 wave possible; 100 duplicate role comments create only one registration, not 100 workers. FIRST role change after initial join is allowed immediately; later changes require >=600 sim ticks after preceding change. At most one active role per player and boundary. Boss appears tick2600 before combat boundary, so two resolution opportunities at tick2600/2800. At tick2800 combat resolves BEFORE entering RESULTS. No viewer wave triggers WAITING not endless losses. No game clock catches up while provider is down. A role action at t=299.9s is assigned NEXT wave; replay must preserve acceptance tick exactly.

## Mandatory edge case resolutions
- New session WAITING has wave_tick=-1; first eligible join starts tick0 (no XP or combat on tick0). At tick3000 queued NEXT-wave roles start next wave tick0 automatically; if no queued participants, WAITING=-1.
- First valid role switch after initial join may happen immediately; subsequent role switches require >=600 simulation ticks from the last accepted switch. Same-role duplicates do not use the switch. No identity may occupy two roles at a boundary.
- Militia for 1<=P<=10 prevents 3-to-4 participant cliff without pretending NPCs are viewers. No rule guarantees victory to every all-builder/all-defender composition.
- At boss waves, ordinary HP=0 before tick2600 means BOSS INCOMING, never early victory. Final combat at tick2800 precedes RESULTS settlement. DEFEATED skips all remaining builder/combat/XP work, not just incoming damage.
- Victory increments total_wins and caps consecutive_wins at10; village_level=min(50,1+floor(total_wins/3)). Game math uses checked signed int64 and bounded resources. At tier20 construction work is ignored, and no partial work consumes stone; at most one wall upgrade per boundary.
- Only one +10 XP per member per wave after an eligible contributing boundary. Progress is cosmetic only; no paid/gift power, repeat-chat XP, manufactured viewers or falsely victorious banners.

## Balance calibration gate
The coefficient 18 for fighter damage is a provisional fixed implementation baseline selected after exploratory algebra for 10–30-person boss waves. It is NOT a claim of observed viewer enjoyment. Before implementing combat, generate executable independent reference vectors for P=1,3,4,5,10,30,100,1000,10000; role splits 0/25/50/75/100% fighters; boss and ordinary waves; consecutive_win 0/3/9; loss recovery 0/1/3. Verify exact tick2800 outcome, bounded resources, no hidden bosses and no loss spiral. Any balance change requires explicit rules_version bump, QA acceptance and updated golden vectors.

`tooling/refeval` is the independent executable evaluator for this gate; `tooling/refeval/testdata/golden_vectors.json` holds the accepted vectors. Its first run (M00) measured the minimum fighter count that clears a boss wave at d=1, no prior losses and no vote: P=1..4 requires 0 fighters (militia alone suffices), P=5 requires 1, P=10 requires 4 (40%), P=30 requires 9 (30%), P=100 requires 25 (25%), P=1000 requires 196 (19.6%), P=10000 requires 1849 (18.5%). Two accepted characteristics follow and MUST NOT be "fixed" without a documented rules_version bump: (i) the required fighter share is NON-monotonic in population and peaks around P=10 because the militia falls off faster than enemy HP rises; (ii) at 0% fighters a wave is lost at P>=5 but won at P<=4, and at 25% fighters most P=10 and many P=30 waves are lost while P>=100 wins. These are difficulty/composition properties, not unstated rules; the recovery modifier (55% enemy HP after three consecutive losses, with consecutive_wins reset to 0 on a loss) bounds any spiral for a fixed composition, so a losing composition that adds fighters or absorbs losses becomes winnable again.
